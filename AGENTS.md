## Commands
- Setup/repair: `bash install.sh` (`--plan` preview GPU plan, `--check`, `--repair`, `--cpu`, `--gpu <vendor>`); dev extras: `uv pip install --python .venv/bin/python -e '.[dev]'`.
- Tests: `.venv/bin/python -m pytest -q -p no:cacheprovider --ignore=tests/test_vram.py` (full suite ~21 min); one file: `.venv/bin/python -m pytest tests/test_x.py -q`. `make test` = verbose full run incl. GPU tests.
- Lint: `.venv/bin/ruff check src/ scripts/` (must stay clean; `tests/` has ~108 legacy findings). `make lint` hides failures (`|| true`) — never trust it.
- Run: `make run` (= `bash run.sh`, uvicorn :7860). Prefer the service: `systemctl --user restart finetune-studio`; logs `journalctl --user -u finetune-studio -f`.
- Accelerator check: `.venv/bin/fts accel` (nonzero only on a GPU host that fell back to CPU).
- Symbols: `make codemap` / `.venv/bin/python scripts/codemap.py --grep NAME`; `make codemap-check` fails on drift.
- E2E browser suite: `tests/run_qa.sh` (see `tests/README_E2E.md`; can mutate live data).
- Deploy: `git push`, then on the host `bash update.sh` (non-interactive: pull ff-only, venv health, deps + torch pin, llama.cpp, DB migrate, restart). (Re)install unit: `bash install-service.sh`. Details: `RESTART.md`, `docs/DEPLOYMENT.md`.
- Verify before "done": the changed module's test file + ruff pass; GPU-path changes need a real GPU run noted in HANDOFF.

## Conventions
- New code goes in the module that already owns the concern (check CODEMAP); new feature → new module + new test file, not a bigger file. Run `make codemap` after adding/moving/renaming symbols.
- Type hints on every signature; Pydantic/dataclass models for anything crossing the API boundary.
- HTTP: reuse what the module already uses (`urllib.request`/`httpx`); do not add a new HTTP library.
- Device code goes through `finetune_studio.accel` — never hard-code `cuda`, `{"": 0}`, `bf16=True` or bitsandbytes.
- Errors are honest: real 4xx/5xx with a reason, never 200 `{error}` or a silent fallback.
- Commits: imperative "what + why", one logical change each; the pre-commit hook bumps `VERSION` (run `make hooks` once per clone; skip with `FTS_NO_BUMP=1`).

- `scripts/corpus_review.py apply`: a line `<id> E question || answer` keeps `#` inside the edit (only verdict lines are comment-stripped); `apply` also works on already-approved pairs (use it to correct a pair a later source supersedes, e.g. the Oakhaven credit EUR 14,500 → 12,750).
- GGUF of a 9B takes ~8 min (f16 → quant): give browser/driver waits >= 900 s (`FTS_EXPORT_TIMEOUT`); the app stayed at <= 40 ms during it. The harness journal watcher ignores the app's own handled "merge base does not fit on cuda" fallback.
- Pairs review page (`data_prep.html`, JS prefix `rq*`): list = `GET data-prep/qa/queue` (slim, paged, document order, project-wide counts), pane = `.../qa/{id}/context` (full chunk), verdicts are optimistic + saved in order (`rqSend`), `PATCH`/`bulk` stamp `reviewed_at` (a human verdict; `status` without it = machine-approved), `POST data-prep/qa` adds a reviewer pair (`origin=human_review`). `list_qa_pairs` is stat-validated per file (`_PAIR_CACHE`), safe against other writers. A background load must never rebuild the pane (`_rq.shownId`); anything async that changes the list must count in `_rq.inflight`. `scripts/bench_review_page.py` is the latency test (~30 ms/verdict).
- UI-only review replay: `corpus_review.py plan --ui` (golden prefill by identical file+chunk+question+answer, multiset for duplicates), `apply --ui` / `add --ui` write `.tmp/ui-verdicts.jsonl` (last verdict per id wins), `e2e_track_a.py --phase a_review_ui` replays them with the keyboard and stops at the first pair without a verdict; `a_adds_ui` adds reviewer pairs for facts still uncovered. Golden files named `approved*`/`rejected*` feed `plan`; the run-2 archives are `ui_run_*` on purpose.
- Testing page quiz import (`testing/suite_import.py`, `POST /api/benchmarks/projects/{pid}/suites/import`): `{id,q,expect:[...]}` becomes a case whose answer key is the expected values (`; `-joined, also listed to the judge as key values); `"expect_abstain": true` marks a question the documents do not answer (the judge is told declining is correct). Run suites on the q4_k_m GGUF: the HF merged bf16 needed > 40 min for 122 questions. The Testing model list is project exports only (no untrained base; pass `model_path` to the API for one).
- Agent shell: a leading standalone `sleep N` is blocked and a foreground call dies at 600 s (exit 137 even with `timeout 580`): wait with `timeout 480 tail -f /dev/null; <check>`, start long jobs with `nohup ... &`, poll their log.
- Run-then-judge (Genor 2026-10-09; `docs/judging/RUN-THEN-JUDGE.md`): a test RUN saves raw transcripts (question, model answer, answer key) with NO verdict; correctness is decided afterwards by an AI judge (`testing/judge.py`, any provider row, default = helper seat) and/or the human (UI), appended to `case_judgements` (human > ai > exact > scripted; `benchmark_cases.verdict` is just the effective one). No scripted/substring/keyword matcher may decide correctness of a user's own Q&A: the only exact scoring left is `strict_scoring.apply_exact_scoring` for public/built-in MCQ+numeric suites (`suite_defs.scoring_mode_for_suite`; the Benchmarks route refuses a quiz with 400). A failed judge call leaves the case unjudged (error stored), never `fail`; `pass_rate` is `None` while nothing is judged. Auto-judge is a saved setting, default OFF (`/api/settings/testing`).
- Test/judge jobs (`webui/testing_jobs.py`): asyncio tasks holding `ENGINE_LOCK` for the whole run (nothing may swap the model between two questions); a local-GGUF judge unloads the tested model first (`open_judge`), an API judge needs no GPU; a second GPU job is 409 (never queued); progress lives on the `benchmark_runs` row and a restart marks interrupted jobs failed (`db.reconcile_stale_benchmarks`). The route resolves the model (explicit or latest merged export), never "whatever is loaded".
- Sandbox DB: `settings.db_path` is cwd-relative (`FTS_DB` only moves the providers DB): a `python -c` one-liner from the repo cwd that calls `init_db()`/`create_project` writes the LIVE `data/finetune_studio.db`. Run sandboxes from a temp cwd (`.tmp/sbx/run_sandbox.py` pattern: fake engine + fake `open_judge`, redirected HOME).
- RAG chunks are whole lines (`data/rag_portable/chunking.py`): never `split()`/re-join a document's text, that fuses a table row's last cell with the next row's first; size in embedder tokens (`encode.count_tokens`). Default retrieval depth is `DEFAULT_TOP_K` (constants.py), not a literal 5. Indexes built before this keep word chunks until rebuilt.
