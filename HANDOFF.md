# HANDOFF — finetune-studio

## Mission
Trained models must reliably answer the learned corpus without inventing database sources. Every parsed chunk must reach the training dataset; judge by transcript review, not auto-green tests.

## State (verified 2026-09-30)
- **Confirmed real: approved/covered QA pairs were silently dropped from the exported training dataset by a cross-source dedup bug (fixed).** Genor's standing concern — "does the dataset really cover 100% of the source info, or do we just trust a number" — turned out to have a real hole. `deduplicate_qa_pairs` (`data/prep/export.py`, shared by both `export_qa_jsonl` and the subset-build path) keyed solely on `question.casefold()`, with no `source_id` or `chunk_idx` in the key. Two unrelated sources whose auto-generated questions happened to collide (proven with real data: 5 CSV test files sharing an identical header row all produced the byte-identical coverage_fill question "According to the source document, unit_id | class | status | fuel_pct | last_service ---?" despite completely different row data; a DOCX/PDF pair of the same content collided too) silently lost the loser's entire answer — even though the per-source coverage gate (`data/prep/coverage_fill.py`) had already certified every one of those sources as 100% covered. Confirmed via `GET /api/projects/{pid}/data-prep/audit` (a real, already-existing deterministic audit endpoint — re-hashes raw bytes, re-parses, re-chunks, checks grounding — but it's API-only, no UI page calls it) plus direct inspection of the exported `.jsonl`: 6 of 102 sources were completely absent from a "100% coverage" dataset build. **Fixed**: dedup key is now `(source_id, chunk_idx, question.casefold())` — a chunk re-asking the identical question twice still collapses to one target (original intent preserved), but two different sources/chunks never collide. Re-verified live: rebuilt the same 102-source dataset, all 102 now present (was 96), 227/227 approved pairs exported (was 199 — some were missing entirely, not just from the affected 6). New regression tests in `tests/test_qa_export_dedup.py` pin this. Traced the rest of the chain empirically too (`load_jsonl` → `format_for_sft` → `split_data` → training worker): 227 loaded → 227 formatted → 204 train + 23 val = 227, zero loss for real exported data. `format_for_sft` does have unlogged `continue` skip-paths for malformed rows (dead for our own valid sharegpt export today, but worth an explicit count/log so a future format regression can't silently repeat this bug) — see Next steps.

- Fixed a real bug found during this pass: `fd3b843` — the project wizard's Step 4/5 status widgets and its auto-test flow called `GET /api/training/runs?project_id=PID`, but that query string is silently ignored by the `/runs` route (which lists every project's runs); the project-scoped route is `/runs/{pid}`. A brand-new project's wizard was showing another project's run count and loss. Fixed all three call sites.
- **Context-length default was below the intended 32k floor in several load paths (fixed 2026-09-30).** GPU-offload was already correctly hardened (`GH-AAA`, `models.py`): any request for partial/zero GPU layers is unconditionally coerced to `n_gpu_layers=-1` (full GPU), and the loader shrinks `n_ctx` on OOM instead of ever falling back to mixed/CPU offload — that part was not a bug. But `n_ctx` itself defaulted to 16384 (`models.py` load + memory-estimate routes, `chat_v2.py` load + memory-estimate, `providers.py`'s `LocalGGUFProvider`) or 4096 (`testing/inference.py`'s `load`/`_load_gguf`/`estimate_memory` signatures — silently used by `benchmarks.py`'s judge-model load and `testing.py`'s test-page load, which call `.load(model_path)` with no `n_ctx` at all) instead of the 32768 floor `helper.py`'s built-in agentic helper already used correctly. Raised every one of those defaults to 32768, plus the `inference.html` UI slider (was hardcoded to 16384) and its GPU-layers tooltip (was stale copy describing "partial offload is supported" — the control has been disabled/forced-full-GPU-only for a while). Verified live: loaded `model-q4_k_m.gguf` through the real UI with no explicit overrides → page showed `GPU offload layers: all`, `Context length: 32768`, `nvidia-smi` showed the process holding real VRAM (no CPU spillover). Full pytest suite (1143 passed) confirms no regressions.
- **`.venv` was missing the `parsers` extra entirely (fixed 2026-09-30).** `install.sh`'s base install ran plain `-e .`, never `.[parsers]` — so `pypdf`/`python-docx`/`openpyxl`/`xlrd`/`python-pptx`/`beautifulsoup4`/`striprtf`/`Pillow` were never installed by a native install on a genuinely fresh machine. Today's 102-file/12-format QA pass only worked because this dev venv already had those packages from unrelated earlier work — not because install.sh provisions them. `install.sh` and `update.sh` now install/sync `.[parsers]` (folded into the base install, since parsing is core functionality, not an optional extra like unsloth/abliteration). `scripts/update.sh` already installed `.[all]` (which includes `parsers`) — no change needed there. Applying `.[parsers]` to this venv also corrected drift: `transformers` had silently climbed to 5.17.0 (above the stated `<5.0.0` cap) from an earlier unrelated `pip install`; it's back to the pinned 4.57.6 family.
- **Model-loading was 5+ independent implementations; consolidated into one (2026-09-30).** Genor's complaint: "we can't have 5 load functions for model code, one true way of being done." Verified true: `LocalGGUFProvider.load()` (models/providers.py) and `InferenceEngine._load_gguf()` (testing/inference.py) each independently built `llama_cpp.Llama(**kwargs)` — one had OOM-retry (shrink context, never mixed offload), the other had mmproj/vision detection and KV-cache-type support, neither had both. Separately, `models.py`, `chat_v2.py`, `testing.py`, and `data_prep.py`'s `/providers/{pid}/load` each had their own copy-pasted "force n_gpu_layers=-1" guard — `chat_v2.py`'s had silently drifted and didn't enforce it at all, meaning that one route alone would have allowed mixed CPU/GPU offload. New `models/llama_loader.py` is now the single home for both: `load_llama_gguf()` (the actual Llama() builder — OOM-retry + mmproj + KV-type, used by both provider and engine) and `resolve_loader_overrides()` (the request-body → loader-kwargs + GH-AAA guard, used by all four routes). `DEFAULT_N_CTX` is the one constant every default now points at (`helper.py`, `providers.py`, `testing/inference.py`'s three signatures, both memory-estimate routes) instead of five separately-typed `32768`/`16384`/`4096` literals. Deleted `models/loader.py`'s `load_for_inference`/`load_gguf_inference` — a third, entirely dead Llama-construction path with zero callers. 9 new tests in `tests/test_llama_loader.py` pin the OOM-retry, mmproj-detection, and KV-type behavior directly so neither caller can silently lose a feature the other has again. Verified live through the real browser: a custom context value set on the data-prep page's helper-load field flows through `resolve_loader_overrides` → `ModelManager.load` → `LocalGGUFProvider.load` → `load_llama_gguf`, confirmed via `nvidia-smi` (correct VRAM for the requested context) and the provider's own `describe()` (`n_ctx`, `gpu_layers_on: 48/48`).
- **User overrides for context length are no longer confined to one hidden page (fixed 2026-09-30).** Also from Genor: an override set on `/inference` only applied to that one in-memory load — `ModelManager.load()`'s own docstring said so explicitly ("without a DB write"). The very next auto-load from data-prep, RAG, or anywhere else would silently discard it and fall back to the stale persisted default. `ModelManager.load()` now writes an explicit override back to the provider's persisted `extra` row, so changing it anywhere makes it the shared default everywhere. Added inline context-length fields at the two most-used trigger points that had none at all: data-prep's "Generate pairs" helper auto-load (`prep-helper-ctx`, synced from and written back to the real persisted state) and the project chat page's inline model loader (`chat-inline-ctx`). Both verified live via real browser clicks + `nvidia-smi` VRAM confirmation, not just code review.
- **Two independent "currently loaded model" trackers could both hold a resident model at once, doubling VRAM use (fixed 2026-09-30).** The global `inference_engine` (testing/chat/RAG/benchmarks) and `ModelManager`'s active provider (data-prep's helper, `/api/providers/*`) were never coordinated except at one spot (`/api/models/unload`, which a prior fix — comment cites "E2E-22" — already made free both). `benchmarks.py`'s judge-model load and `training.py`'s pre-training unload each only freed `inference_engine`; a data-prep helper loaded via `ModelManager` stayed resident through the whole judge run or training run. Worse, none of the four `/load` routes freed the *other* engine before loading into their own — routine page navigation (load a helper in data-prep, then open the chat page and load a different model) could double-load VRAM with no unload click involved at all. New `unload_all_models()` in `models/llama_loader.py` is the one function every unload site and every load site (before loading) now calls. Verified live, not just mocked: loaded the 12B helper via `ModelManager` (13,578 MiB), then loaded an unrelated model via `inference_engine` (chat-v2) with zero explicit unload step — VRAM dropped to 1,378 MiB before the new model loaded, `ModelManager`'s active provider correctly showed `None`. Confirmed the reverse direction too (loading via `ModelManager` while `inference_engine` held a model). 3 new tests in `test_llama_loader.py` pin the behavior, including that one engine failing to unload never blocks freeing the other.

## Known issues (found 2026-09-30, not yet fixed)
1. **RAG document count inconsistency at scale**: uploading 102 files and building the RAG index reported "Done — 120 docs, 120 chunks indexed", but the actual Documents table showed 127 rows. No duplicate filenames were found in the visible rows, so root cause is unconfirmed — could be a stale/partial index from an earlier build not being cleared, or a display vs. persisted-count mismatch. Needs a from-scratch rebuild + count audit to isolate.
2. **New-project base-model dropdown shows duplicate entries**: 4 indistinguishable rows all labeled "Aethermoor World Bible · Qwen3.5-9B · merged (safetensors, 16.68 GB)" — likely 4 different export runs sharing a display label with no way to tell them apart (missing run ID or timestamp in the label).
3. **No image support in the parser registry** (`data/parsers.py`): `.png/.jpg/.pdf-images` etc. are not a supported source type at all — Pillow is a dependency but not wired to any content-extraction path. Worth a product decision (intentional scope vs. gap) rather than assuming it's a bug.
4. **`antiword`/`pdftotext` are not installed by `install.sh`** (system binaries, not pip packages — `.doc` legacy fallback and one PDF-parse fallback path use them via subprocess). This already degrades gracefully with a clear message rather than crashing, so left as-is; flag if `.doc` support becomes a real requirement.
