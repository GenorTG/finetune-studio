## running it locally

You need Go 1.22, Node 20, Python 3.11 (just for the data tools), Docker with Compose v2, and about 14 GB of free disk. Then:

```
git clone git@git.korvane.example:platform/tidewalk.git
cd tidewalk
make dev-up        # compose stack: postgres, redis, ingest, engine, notifier, console
make seed          # demo data
```

Ports (and why they are weird — they were picked so they don't clash with the other 11 things people run): console on **4300**, public API on **8480**, postgres on **5433**, redis on **6390**, the fake SMS sink (MailHog-style, we call it "Pingless") on **8925**.

`make seed` creates the demo tenant **KT-90001** ("Demo Fruttoria", Plus edition) with 60 synthetic containers, three sites (DEMO-A, DEMO-B, DEMO-C) and the four default profiles. Login: `dev@korvane.example`, password is in the vault at `kv/tidewalk/dev-seed` (rotates monthly, so don't hardcode it). If you break the DB, `make db-reset` takes about 40 seconds. Don't run it against anything but your local stack; it asks "are you sure" but muscle memory is stronger than prompts.

The simulator: `make sim HUBS=3 TAGS=40` starts three virtual KC-Hub 200 gateways with 40 virtual KC-Tag 4 each, reporting every 30 s (like the real ones). `make sim-excursion CONTAINER=cnt_DEMO0007` pushes that container to +9.1 °C for 12 minutes so you can see a CRIT fire. It does *not* fire the real SMS provider — local mode swaps Pingwave for Pingless. If you ever see a real SMS leave your laptop, stop and tell #platform immediately.

## repo layout (the short version)

- `engine/` — rule engine, Go. Hot code. Benchmarks in `engine/bench`, please run them if you touch the evaluator loop. The budget is **2 ms per reading**, p99.
- `notifier/` — dispatch, batching, channel adapters (SMS, mail, webhook, Teams/Slack, voice).
- `ingest/` — receives hub packets, the stuff behind `POST /ingest/v1/packets`.
- `console/` — the web UI, TypeScript/React.
- `api/` — the public API, OpenAPI spec in `api/openapi/v2.yaml` is the source of truth; the developer-portal page is generated by hand (yes by hand, by me, sorry).
- `deploy/` — helm values, overlays, the render scripts.
- `tools/` — python scripts (calibration import, retention dry-run, the usual).

### about `deploy/values/`

This is the part that burned us in August (PM-2024-07 — read it, it's 1,400 words and it's the best-written thing in the company). Since the incident:

1. The staging load-test overlay lives in `deploy/values/overlays/loadtest-staging.yaml`, **outside** the tree that production renders from. Do not copy from it. (Action AI-4.)
2. Platform settings have schemas in `deploy/schema/`. `batch_window_ms` is capped at 30000. CI renders prod values and validates them; if it fails, it fails, no "skip ci" and no override flag. If you think the schema is wrong, change the schema in a separate PR.
3. Any change under `deploy/values/` needs **2 approvals**, and one of them must come from the Platform lead or the deputy (Sanna Virtanen). The reviewer must tick "I read the rendered diff" in the PR template. We know it's theatre unless the diff is small, so keep diffs small.

## workflow

Branches: `feat/TW-1234-short-name`, `fix/TW-1234-short-name`, `chore/...`. The id is the tracker id; no id, no merge. Commits follow conventional commits (`feat(engine): ...`), enforced by commitlint on the PR. Line length 100 for Python (black), `golangci-lint` v1.59 for Go, and Prettier defaults for TypeScript. Test coverage must not drop below **72%** on `engine/` and `notifier/` (CI blocks it); the console has no gate because it has no coverage worth gating, which is a different problem.

CI takes about **14 minutes** on a clean cache. If it takes 40 minutes you are on the old runner pool, ping Aneta.

PRs: one approval normally, two for `deploy/values/` (above) and for anything touching `engine/evaluator`. Squash merge. Merge to `main` deploys to staging automatically; staging is `staging.tidewalk.korvane.example` and its data is refreshed from anonymised production every night at **04:10**.

## things that will trip you up

1. Time zones. The database is UTC, the console shows the tenant zone, and the notifier logs CET/CEST depending on the month, because someone configured it by hand in 2022. Compare logs with `date -u`.
2. `rule.clear.hysteresis_n` is **3** by default; the tests assume that. Don't change the default without changing 41 tests.
3. The rule evaluator re-checks time-based conditions every 30 s. If your test sleeps 29 s and expects a TAGSILENT, you will fail one run in two.
4. Don't parse container ids (`cnt_` + 12 characters). The length changed once.
5. Never log a webhook secret. We have a scrubber, the scrubber has a bug (TW-4140), and we'd like to not find out which log line proves it.
6. ColdLedger is not our system. Don't try to fix it from here.
