Tidewalk Public API — v2 reference

Developers / Tidewalk / API reference

Page owner: Wiktor Szczepaniak · Last edited 30.09.2024 11:42 by bart.o · Applies to Tidewalk 6.5 · Draft status: live

1. Introduction

The Tidewalk public API lets customers and integration partners read containers, readings and alerts, acknowledge alerts, and manage webhooks, without going through the web console. It is a JSON-over-HTTPS API; every request and every response body is UTF-8 JSON, with the single exception of exports, which can also be CSV. The production base URL is https://api.tidewalk.korvane.example/v2. Anything that does not start with /v2 is either a legacy path or a mistake.

All timestamps are ISO 8601 in UTC with a trailing Z (for example 2024-09-18T04:07:31Z), and all temperatures are degrees Celsius with one decimal. Identifiers are opaque strings. Container identifiers look like cnt_ followed by 12 characters, alerts like AL- followed by 7 digits, hubs like hub_ and the hub's name. Please do not parse them; we have changed the length once already and may do so again.

Access is by API key, which a Tenant Admin creates in the console (Admin > Integrations > API keys). How many keys a tenant may hold depends on the edition and is stated in the Administrator's Guide. Everything below is subject to the Tidewalk Terms of Service and the Fair Use Annex, which nobody reads but which does exist.

2. Authentication

Send the key as a bearer token: Authorization: Bearer twk_live_.... Live keys begin with twk_live_ and test (sandbox) keys with twk_test_; the rest of the key is 40 characters of base62. A key is shown once at creation. If it is lost, rotate it. When a key is rotated, the old one stays valid for 48 hours so that deployments can be switched over without a gap.

Keys carry the role Integrator by default, which can read data and acknowledge alerts through the API only if the key was explicitly given the scope alerts:ack. The available scopes are read, alerts:ack, alerts:comment, webhooks:manage, export and audit:read. The last one is available only to keys created by a Tenant Admin whose tenant also has an Auditor.

For partners who need short-lived credentials there is an OAuth 2.0 client-credentials endpoint at POST /oauth/token. Access tokens live for 3600 seconds and cannot be refreshed; fetch a new one. A client secret is valid for 12 months. Client-credentials is available on Plus and Pharma only.

Keys are bound to the tenant that created them. Optionally, a key can be bound to a list of up to 10 source IP addresses or CIDR ranges; requests from elsewhere get a 403 with error code TW-403-02.

3. Rate limits

Limits are applied per key, per minute, using a sliding window. The default is 300 requests per minute, with a burst allowance of 50 requests in any one second. Tenants on Plus get 900 requests per minute and tenants on Pharma 1,800. Some endpoints have their own, stricter limits, shown in the endpoint table.

Every response carries the headers X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset (the last in seconds until the window frees up). When the limit is exceeded the API answers 429 Too Many Requests with a Retry-After header, in seconds. A client that ignores Retry-After and keeps hammering gets a temporary block: 10 consecutive 429 responses lead to a 15-minute block of the key, answered with TW-429-02.

Polling is a poor way to use the API. If you want alerts, use webhooks. If you must poll, poll no more than once per 30 seconds per container list, because the underlying data does not change faster than that (a tag reports every 30 seconds).

Pagination uses an opaque cursor: pass back next_cursor from the previous response as cursor. A cursor expires 10 minutes after it was issued. Do not store them.

Writes accept an optional Idempotency-Key header of up to 64 characters. Repeating a request with the same key within 24 hours returns the original response with the header Idempotent-Replay: true, and does not repeat the action. Reusing a key with a different body is an error (TW-409-01).

Exports produced through the API are kept for 14 days, same as in the console. The download URL returned by GET /exports/{id} is signed and valid for 60 minutes.

4.1 Webhook events

Webhook deliveries have the form {"event": "...", "tenant": "KT-20417", "data": {...}} and are signed as described in the Administrator's Guide (header X-Tidewalk-Signature). The event types are alert.fired, alert.acked, alert.cleared, hub.lost, hub.recovered and test.ping. A delivery has the header X-Tidewalk-Delivery with a unique id, which receivers should use for de-duplication, because the same event may be delivered more than once when a retry is triggered by a slow response (receivers have 8 seconds).

5. Errors

Errors are returned with the matching HTTP status and a JSON body: {"error": {"code": "TW-404-01", "message": "...", "request_id": "req_..."}}. The request_id is what the support desk will ask for first, so please keep it.

For 5xx responses use exponential backoff starting at 2 seconds and doubling up to 64 seconds, with some jitter. If you receive more than five TW-500-00 within one minute, please stop and write to api-support@korvane.example rather than retrying forever. We do monitor, but not at three o'clock in the morning for a partner whose retry loop has a bug.

6. Hub ingest (restricted)

This chapter is for completeness. The ingest endpoint, POST /ingest/v1/packets, is used by KC-Hub 200 gateways, authenticates with the gateway token issued at provisioning and is not available to customer keys. Gateway packets are batched with a maximum of 200 tag readings per request. The ingest service rejects a packet whose hub clock differs from the server by more than 90 seconds, answering with the hub error E-4108, and rejects a request with an unknown or mismatched gateway token with E-4031. Those two hub-side error codes are the reason for most "hub offline" tickets that turn out not to be offline hubs; the on-call runbook has the cures.

7. Sandbox

A sandbox is available at https://sandbox.api.tidewalk.korvane.example/v2. It uses test keys, runs the latest release candidate (at the time of writing 6.6-rc2) and is reset every Sunday at 04:00 UTC, which deletes everything you created. Rate limits in the sandbox are 60 requests per minute for every key. The sandbox contains 40 synthetic containers, and one of them, cnt_SANDBOXEXC01, is always in a CRIT temperature excursion, which is what you want when you test your alert handling and is nothing to worry about.

7.1 Sample: acknowledge an alert

POST /v2/alerts/AL-0418862/ack HTTP/1.1
Host: api.tidewalk.korvane.example
Authorization: Bearer twk_live_REDACTED
Idempotency-Key: 7f0c1c9e-2e2a-4a1d-9f4b-0b6d1f9a7e33
Content-Type: application/json

{
  "comment": "Reefer unit restarted by driver at 04:22, re-check at 05:00",
  "notify_contacts": false
}

A successful response is 200 with the updated alert. The status is then acked and the field ack_expires_at carries the time at which the acknowledgement lapses (4 hours after the acknowledgement, unless the rule says otherwise).

8. Deprecations and versions

API v1 is deprecated and will be switched off on 31 March 2025. Customers still on v1 receive a Warning: 299 header on every response and a monthly e-mail from Yusuf Demirkıran's team, who would prefer to send fewer. v2 has been the current version since 12 March 2023. The minor revisions of v2 are announced in the developer newsletter and are never breaking; we add fields and endpoints, we do not rename or remove. Clients must ignore unknown fields.

A breaking change, when it comes, will appear as v3 with at least 12 months of overlap. A beta of the v3 design for the Tidewalk v7 programme is being discussed with a small group of partners; it is not public and this page does not describe it.
